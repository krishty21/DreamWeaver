     3→## Project Overview
     4→DreamWeaver: a dream capture → AI (Gemini via z-ai-web-dev-sdk) structured analysis → longitudinal pattern memory → interactive Subconscious Arcade (RE-ENTER DREAM with REPLAY/REWRITE/CONFRONT) product.

   200→## Goals / completed modifications / verification results
   201→1. BUG FIX (latent, mobile): horizontal overflow on dream-detail (scrollWidth 723 vs 390) and patterns (650 vs 390).
   202→   - Root causes (two compounding):

   378→## Unresolved issues / risks / next-phase recommendations
   379→- TTS synthesis latency is ~12–15s for a typical dream (~4000 chars → 4–5 chunks). Mitigated by the audio-loading-bar shimmer + "Weaving the narration…" copy. Could be reduced by caching synthesised audio on the server per (dreamId, voice, speed) tuple — left for a future round.
   380→- The Atlas timeline bar uses width=56px per bar; on very long dream histories (>40 dreams) the timeline will scroll horizontally. The `.scroll-elegant` scrollbar styling handles this gracefully. If users complain, a "show all" expandable view could be added.
   381→- The Atlas view's "Open last" button only opens the most recent dream containing that motif. A more advanced affordance would open a stacked list of all dreams with that motif, letting the user pick. Left for a future round.
   382→- The mobile long-press on calendar cells is verified logically (450ms timer + cancel-on-move + swallow-onClick) but agent-browser's `press` doesn't simulate touch events natively, so it was tested by code review rather than live touch. A physical device test is recommended.
   383→- The TTS rate (speed) is baked into the WAV by the SDK — there's no real-time playback rate control without re-synthesising. The UI re-fetches when the user changes speed, which is acceptable for short dream narrations but would be too slow for long-form audio. Acceptable for the dream-read-back use case.
